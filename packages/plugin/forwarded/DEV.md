## 目标

`@produck/kitty-plugin-forwarded` 提供「按 RFC 7239 读取 `Forwarded` 头」的
能力：解析转发链，回答客户端地址与原始协议。

## 已实现

- `_Parser.mjs`：`ForwardedList` / `Element` / `splitOutsideQuotes` / `Unquote`
  - 按 §4 语法拆分 `1#forwarded-element`，逗号与分号在引号内不拆。
  - 参数名折小写；重复参数的元素判无效；无值的 pair 忽略。
  - §5.6.1.2：空列表元素被容忍，但不产生条目。
- `_Concrete.mjs`：`entryList()` / `client()` / `protocol()`
  - `entryList` 按到达顺序返回，索引 0 是链首（最靠近客户端）。

## 潜在问题：信任边界尚未处理

### 现状

`Forwarded` 头由每一跳代理追加（§7.1），但整条链**完全由客户端可控**：
客户端可以自己发送 `Forwarded: for=1.2.3.4`，代理再往后追加。因此：

- 链首（索引 0）不一定是真实客户端。
- 只有在「已知信任边界」右侧的部分才可信。

当前实现**直接返回索引 0 的 `for`**，不区分来源。这与「默认开启」的取舍
一致（不做静默拒绝），但**消费侧必须自己判断是否可以采信**。

### 为什么会成为问题

1. **无配置入口。** `useForwarded(kit)` 不接受可信代理列表，插件无法自行
   判定信任边界。
2. **`obfuscated` 标识符未处理。** §6.3 允许 `for=_hidden` 这类不可路由
   标识符，当前会原样返回，消费侧若直接当 IP 使用会出错。
3. **`for` 带端口或 IPv6 方括号。** §6.2 允许 `for="192.0.2.60:8080"` 与
   `for="[2001:db8:cafe::17]:4711"`，当前原样返回字符串，不拆分。
4. **`unknown` 是合法值。** §6.2 允许 `for=unknown`，同样会原样返回。

### 待定

- 是否引入可信代理配置（CIDR / 地址列表），提供「从右向左剥离」的
  `client()` 语义。
- 是否区分「原始链」与「可信链」两个访问器，避免消费侧误用。
- 是否需要结构化输出 `{ address, port, family }`，与
  `Exchange.local` / `Exchange.remote` 的 `Address` 形状对齐。
- 多数场景下仍需要 `X-Forwarded-*`（无 RFC，但部署广泛）。是否在同一插件
  内处理，或明确拒绝并交由消费方自行解析。
